**版本**：v0.1

**作者**：开发团队

---

## 1. 设计目标

围绕“在 AI 分类流程中对 `single_person` 照片直接触发本地人物归组”的产品策略，完成跨端可落地的技术方案。

核心目标：

1. 在不破坏现有扫描漏斗流程前提下，新增人物归组阶段  
2. 仅依赖本地模型和本地存储，不增加服务端耦合  
3. 支持增量处理、可恢复、可观测  
4. 与现有 `filterType/filterValue` 筛选体系兼容

---

## 2. 现状与差距

## 2.1 现状（代码基线）

- AI分类主流程：
  - PC/通用：`src/services/GalleryScannerService.js`
  - Android原生：`android/app/src/main/java/com/imageclassifier/v2/GalleryScanService.java`
- 分类存储字段：`images.category`（内容分类）
- 统一筛选接口：`UnifiedDataService.readImagesByFilter(filterType, filterValue)`
- 缓存与统计：`GlobalImageCache` 维护各维度 counts

## 2.2 差距

当前系统只支持“内容维度的人物（单人/多人）”，不支持“身份维度的人物（具体某个人）”，缺失：

1. 人脸检测 + 人脸特征向量（embedding）流程  
2. 人物组数据模型（person group）  
3. 图片与人物组的索引关系  
4. `filterType=person` 的读取与缓存统计  
5. 扫描阶段的 `person_indexing` 进度通道

## 3. 总体架构

```text
AI分类阶段（已有）
  -> 得到 category
  -> 过滤 category == single_person
  -> PersonIndexOrchestrator.enqueue(images)
       -> FaceDetectService
       -> FaceEmbeddingService
       -> PersonClusterService
       -> PersonRepository 持久化
  -> 更新缓存与“按人物”统计
```

架构原则：

- **轻耦合**：人物流程通过队列与分类流程衔接，不嵌入分类核心逻辑
- **可降级**：人物流程失败不影响 AI 内容分类结果
- **可扩展**：后续可扩展到 `social_activities`（多人图）

## 4. 数据模型设计（MVP）

> MVP 聚焦单人照片，采用“一图一个 personId”模型，后续再演进一图多人的关系表。

## 4.1 images 表扩展字段

在 `images` 表新增：

- `personId TEXT`：所属人物组ID
- `personConfidence REAL`：人物归组置信度
- `personIndexStatus TEXT`：`pending|done|skipped_no_face|skipped_quality|failed`
- `personModelVersion TEXT`：用于增量重建判断
- `faceBox TEXT`：人脸框（JSON字符串，MVP可仅存主脸）

索引：

- `CREATE INDEX IF NOT EXISTS idx_personId ON images(personId);`
- `CREATE INDEX IF NOT EXISTS idx_personIndexStatus ON images(personIndexStatus);`

## 4.2 person_groups 新表

```sql
CREATE TABLE IF NOT EXISTS person_groups (
  id TEXT PRIMARY KEY,
  name TEXT,
  avatarImageId TEXT,
  embedding TEXT,        -- 人物中心向量（可用JSON/base64）
  sampleCount INTEGER DEFAULT 0,
  imageCount INTEGER DEFAULT 0,
  createdAt TEXT,
  updatedAt TEXT,
  status TEXT DEFAULT 'active'
);
CREATE INDEX IF NOT EXISTS idx_person_groups_imageCount ON person_groups(imageCount DESC);
```

说明：

- `embedding` 存人物中心向量（centroid），用于快速匹配
- `imageCount` 作为首页与列表统计字段

## 4.3 未来演进（非MVP）

当支持多人图时，引入 `image_person_links` 与 `person_faces` 表，替代当前“一图一个personId”设计。

## 5. 模型与算法设计

## 5.1 模型建议

1. **Face Detector**：轻量人脸检测模型（ONNX）  
2. **Face Embedding**：ArcFace/MobileFaceNet 类特征模型（ONNX）

存放位置：

- `public/models/...`（PC）
- Android 通过 `android/app/build.gradle` 已有 assets 映射 + `ModelPathAdapter.ensureModelExists` 复制到文档目录

## 5.2 单图处理流程

1. 加载图片像素
2. 检测主人脸框（只取最高质量主脸）
3. 质量校验（人脸尺寸、检测置信度、清晰度阈值）
4. 人脸对齐 + embedding 推理
5. 与现有人物组 centroid 计算余弦相似度
6. 阈值判定：
   - `score >= T_match`：归入已有人物组
   - `score < T_new`：新建人物组
   - 中间区间：标记待确认（MVP可先归最近组并打低置信度）

## 5.3 阈值建议（初始）

- `T_match = 0.62`
- `T_new = 0.50`
- 检测置信度下限 `det_conf >= 0.75`
- 人脸最小尺寸（短边）`>= 80px`

> 阈值需通过测试集与真机样本校准，支持配置化。

## 6. 流程集成设计（重点）

## 6.1 集成策略

**策略A（推荐）**：  
在 AI 分类结果入库后，提取 `single_person` 图片并提交人物索引队列。

这样满足“嵌入 AI 流程”的产品诉求，同时保持模块边界清晰。

## 6.2 PC/通用端接入点

文件：`src/services/GalleryScannerService.js`

关键接入位置：

1. 缓存命中批量更新后（`ImagesClassificationCachCheck`）
2. 远程推理批量更新后（`classifyImagesbyLLM`）

伪代码：

```javascript
const updated = classificationDataArray.filter(x => x.category === 'single_person');
await personIndexOrchestrator.enqueue(updated, { stage: 'remote_inference' });
```

## 6.3 Android接入点

推荐将人物索引逻辑放在 JS 层统一实现，避免 Java 层重复维护 ONNX 推理链。

接入方式：

- 原生 `GalleryScanService.java` 完成 AI 分类后发送 `ai_classification_completed`
- `GalleryScannerService.android.js` 在事件回调中：
  1. 读取本次新增/更新的 `single_person` 图片
  2. 调用同一个 `personIndexOrchestrator.enqueue(...)`

收益：

- PC/Android 共用一套人物算法与阈值
- 降低跨语言维护成本

## 7. 新增服务与职责

## 7.1 PersonIndexOrchestrator（新增）

职责：

- 接收待处理图片队列
- 控制并发、重试、断点续跑
- 统一上报 `person_indexing` 进度

## 7.2 FaceDetectService（新增）

职责：

- 模型加载与复用
- 输出主人脸框与检测置信度

## 7.3 FaceEmbeddingService（新增）

职责：

- 人脸裁剪、对齐、归一化
- 输出 embedding 向量

## 7.4 PersonClusterService（新增）

职责：

- 与 `person_groups.embedding` 做相似度匹配
- 执行“归组 / 新建组 / 待确认”决策
- 更新 centroid 与 group 统计

## 7.5 PersonRepository（新增）

职责：

- 封装 `person_groups` 与 `images.person*` 的读写
- 提供人物列表、人物详情查询接口

## 11. 失败处理与幂等

## 11.1 幂等键

建议使用：

- `image.id + personModelVersion + imageHash`

若未变化则跳过重复计算。

## 11.2 失败分类

- `skipped_no_face`
- `skipped_quality`
- `failed_model`
- `failed_io`

失败不影响主流程，允许后续重试。

---

## 12. 性能设计

1. 批处理：每批 20~50 张（按设备动态）  
2. 并发：默认 1~2（移动端保守）  
3. 异步：人物索引与主分类解耦，不阻塞扫描完成事件  
4. 增量：仅处理新增/变更的 `single_person` 图片

## 14. 风险与应对

1. **误归组**：提供待确认状态与后续手动合并能力  
2. **性能波动**：开关控制 + 增量策略 + 低并发  
3. **模型体积**：选轻量模型并复用现有模型分发机制  
4. **跨端一致性**：统一 JS 人物服务，避免 Android Java 与 JS 双实现漂移
